# StudyFlow AI — Project Overview

> Generated by a full-codebase audit on 2026-06-24. This document describes the system **as actually implemented**, which differs in several material ways from `README.md`.

---

## 1. Purpose

StudyFlow AI is an AI-assisted study-planning SaaS for students preparing for exams. Users enter subjects/topics (manually or by importing a PDF syllabus), the app generates a difficulty-aware day-by-day study schedule, tracks completion, visualises progress, and offers an AI study coach. It is monetised through a Razorpay-based subscription (monthly / yearly / lifetime) with coupon support and an admin panel.

## 2. Target Users

- Students (school, college, competitive-exam) who need a structured revision plan.
- Primary market signals point to **India**: currency is INR/paise throughout, Razorpay is the payment gateway, dates are formatted `en-IN`.

## 4. Tech Stack

**Frontend** (`client/`)
- React 18.3, Vite 5.4
- Recharts 2.12 (charts), lucide-react (icons), jspdf 4.2 (PDF export)
- **No CSS framework** — inline style objects + `global.css` CSS custom properties (dark/light theme)
- **No router** — tab navigation via `useState`
- ESLint 9 declared but **no config file present**; no TypeScript; no tests

**Backend** (`server/`)
- Node.js (ESM), Express 4.19
- MongoDB Atlas + Mongoose 8.5
- Auth: `jsonwebtoken` 9, `bcryptjs`, `cookie-parser` (JWT in HttpOnly cookie)
- Security middleware: `helmet`, `express-rate-limit`, `express-mongo-sanitize`
- Uploads: `multer` (memory), `pdf-parse`
- Email: `nodemailer` (Gmail)
- Payments: `razorpay`
- AI SDKs: `groq-sdk`; Mistral called via raw `fetch`
- Declared-but-unused deps: `morgan`, `p-limit` (see CODE_QUALITY_AUDIT)

**AI integrations**
- **Groq** (`llama-3.3-70b-versatile`) — chat coach + regen advice (`ai.controller.js`)
- **Mistral** (`mistral-small-latest`) — syllabus PDF → structured subjects/topics (`syllabus.controller.js`)
- ⚠️ `README.md` claims "Anthropic Claude (`claude-sonnet-4`)" — **this is false**; no Anthropic SDK or key is used.

**Payments**: Razorpay Orders API, HMAC signature verification on `/verify`, webhook handler (currently non-functional — secret is a placeholder).

## 5. Architecture

```
Browser (React SPA, Vite dev proxy :3000 → :5000)
   │  fetch(credentials:'include')  cookie sf_token (JWT)
   ▼
Express app (server/src/app.js)
   ├─ helmet, cookieParser, CORS(allowlist)
   ├─ /api/payment            (mounted BEFORE express.json — raw body for webhook)
   ├─ express.json(5mb) + mongoSanitize + requestLogger + global rateLimiter
   ├─ /health
   ├─ /api/ai           protect → requirePro → rate limits
   ├─ /api/schedule     protect (+ requirePro on /generate only)
   ├─ /api/subjects     protect → requirePro     ← UNUSED by client
   ├─ /api/auth         (login/signup/otp/profile)
   ├─ /api/syllabus     protect → requirePro → multer → magic-byte check (SSE)
   ├─ /api/admin        adminGuard (x-admin-secret)
   ├─ /api/cancellation protect
   └─ /admin-panel      HTTP Basic (ADMIN_SECRET) → serves admin-panel.html
   ▼
MongoDB Atlas (Mongoose)
```

State is **dual-sourced**: client keeps planner state in `localStorage` AND mirrors it to the server via `PUT /api/schedule/full` (debounced 2s + `beforeunload` keepalive flush). A `savedAt` timestamp picks the newer of local vs server on hydration.

## 8. Database Design

- **User**: name, email(unique), password(bcrypt), tokenVersion, isPro, paidAt, paymentId, planType, subscriptionExpiresAt, aiMessageCount, reset/cancel OTP fields. `timestamps`.
- **Subject**: userId(indexed), name, color, topics[{name,difficulty,status}]. *(written via API only in the unused subjects flow)*
- **StudyPlan**: userId(indexed), examDate, dailyHours, schedule[day{date,sessions[]}], **subjects (Mixed)**, dayIdx, overflowCount. **This is the real persistence store used by the app.**
- **Payment**: userId, razorpay ids/signature, amountPaise, originalAmountPaise, couponCode, discountPct, planType, status.
- **Coupon**: code(unique), discountPct(10–100), maxUses, usedCount, expiresAt, isActive + virtuals `isValid`/`remainingUses`.
- **Pricing**: planType(unique), name/label, pricePaise, originalPricePaise, isEnabled, badge, description, sortOrder, durationDays.
- **CancellationRequest**: userId, status(pending/approved/rejected), reason, adminReason, usageSnapshot.

## 9. Authentication Flow

1. Signup → validate → bcrypt hash → create user (no auto-login; returns user, redirects to login).
2. Login → bcrypt compare → sign JWT `{id, tv}` → set HttpOnly cookie `sf_token` (7d).
3. `protect` middleware reads cookie (or `Bearer` fallback), verifies JWT, checks `tokenVersion`, auto-downgrades expired timed plans. 60s in-memory user cache.
4. Logout / logout-all → increment `tokenVersion` (invalidates all tokens) + clear cookie.
5. Forgot-password → 6-digit OTP (bcrypt-hashed, 10-min) emailed → verify → reset (gated by `resetVerified` flag).
6. Password change & subscription cancellation are also OTP-gated.

## 10. AI Integrations (detail)

- **Chat** (`POST /api/ai/chat`, Pro): builds a system prompt with exam date, daily hours, %, subject summary; sends to Groq; increments `aiMessageCount`.
- **Regen advice** (`POST /api/ai/regen-advice`): short motivational message from Groq. **Not Pro-gated server-side** (client-gated only).
- **Syllabus import** (`POST /api/syllabus/import`, Pro): SSE stream; extracts PDF text (`pdf-parse`), truncates >80k chars, prompts Mistral to return JSON subjects/topics with difficulty, has truncated-JSON repair + retry.

## 11. Subscription / Payment Integration

- Plans/pricing are **DB-driven** (admin panel is source of truth; frontend price is ignored server-side — good).
- `create-order`: validates plan, applies coupon, creates Razorpay order (or grants free access if coupon → ₹0).
- `verify`: HMAC-SHA256 of `order|payment` with key secret; idempotent update; grants Pro; emails receipt.
- `webhook`: HMAC of raw body with `RAZORPAY_WEBHOOK_SECRET` — **currently rejects all events** because the secret is left at its placeholder value.
- Cancellation: user submits OTP-verified request → admin approves/rejects (manual refund workflow).

## 13. Key Discrepancies vs README

1. AI provider is **Groq + Mistral**, not Anthropic Claude.
2. Auth, payments, admin, coupons, cancellations exist — README lists them only as "roadmap".
3. The documented REST surface (`/api/subjects`, `/api/schedule/generate`) is **implemented but not used by the client**; the app persists everything through `/api/schedule/full`.
4. "MongoDB optional / in-memory store works out of the box" is **false** — `connectDB()` calls `process.exit(1)` on failure; the app cannot run without MongoDB.
